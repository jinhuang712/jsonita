一 · 设计

1设计目标与边界

i18n 在 Jsonita 是架构准备而不是 v1 功能 ── 五条硬约束：

原则含义实现影响
v1 实施期 lockv1 仅交付英文，但所有 UI 文案必须经 t() 函数 ── 不允许 hardcode 英文字符串M0 起就引 react-i18next，所有组件按规范写
Rust 端不翻译Rust 返回的错误 JsonitaError 永远是英文 + kind；翻译在前端按 kind 映射跨 IPC 协议稳定，不受语言切换影响；error.kind 是契约的一部分（13 § 1）
JSON 内容不受 i18n 影响用户输入的 JSON 中含 CJK / 阿语 / 表情 ── 永远透传，编辑器渲染由 CodeMirror 处理i18n 只影响 chrome（菜单 / 按钮 / 状态栏 / Modal；Toast 为保留设计）
实时切换用户切语言 → React 全量 re-render，无需 reload 窗口所有文案经 hook 订阅 store，避免硬编码 prop drilling
包内置不下载语言包打入 bundle（不从远程拉）── 离线可用，且符合 v1 "不联网" 约束v1 / M3 都是 2 个 locale (en-US / zh-CN)，bundle 体积可控（每 locale ~10 KB）

2关键设计决策

2.1i18n lib 选型

方案体积类型友好命名空间结论
react-i18next（选）~30 KB gzippedTS plugin 提供 key 自动补全原生 namespace + 懒加载生态最熟；与 zustand 兼容；fallback chain 内置
lingui~15 KB编译期提取 key（macro）需自己组织体积小但 macro 增加 build 复杂度；ICU MessageFormat 对我们简单场景过度
react-intl (FormatJS)~50 KB（含 ICU runtime）OK需自己组织体积偏大；ICU 强大但 Jsonita 不需要复数 / 性别变体等高级特性
自写~2 KB无无省体积但要自维护 fallback / 复数 / 格式化 / TS 类型 ── 性价比低

2.2资源 namespace 划分

按章节模块拆 namespace，而非按"类型"（按钮 / 标签 / 错误）拆。理由：组件改名 / 移位时改文案文件位置和组件位置一致，定位快。

namespace覆盖范围典型 key
shellFloatingWindow / TabBar / StatusBarshell.tabBar.format · shell.statusBar.valid
panes5 个功能面板的标题、placeholder、empty statepanes.tree.emptyState · panes.aiFix.acceptButton
settings设置 Modal + 6 个分组 + 字段标签settings.general.launchAtLogin · settings.ai.testConnection
history保留 namespace；历史 Modal / Item UI 当前未实现history.filterPinned · history.confirmClear
errorsJsonitaError 9 个 kind 映射 + UI 行动文案errors.parse.title · errors.rateLimit.retryAfter
aboutAbout 页（版本 / 链接 / 致谢）about.version · about.openSourceCredits
common跨 namespace 通用词（OK / Cancel / Confirm / 12 个 base）common.ok · common.cancel

2.3locale 检测与切换

三层 fallback chain，显式优先于隐式：

切换时机：用户在 Settings → General → Language 改 locale → settings_set({ locale: 'zh-CN' }) → Rust emit settings:changed → 前端 store update → i18n.changeLanguage → React 重渲染。无需 reload 窗口。

2.4Rust 错误为何不翻译

  • kind 是契约：JsonitaError.kind 是跨 IPC 的稳定标识符（13 § 1），用于 UI 分级响应（02 § 3.3）。若 Rust 翻译，前端按 kind 映射文案的链路就被打破
  • 错误日志稳定：日志和 issue 报告中错误信息都是英文 + kind，便于跨语言用户提交 bug
  • 前端单源：所有用户文案都在 errors.* namespace，集中维护

映射示例：Rust 返 { kind: 'RateLimit', data: { retryAfterSec: 30 } } → 前端 t('errors.rateLimit.retryAfter', { sec: 30 }) → 中文显示"请 30 秒后重试"。

二 · 工作机制

3加载与切换数据流

3.1资源懒加载

启动只加载当前 locale 的全部 namespace（en-US 或 zh-CN）。切换到另一 locale 时 dynamic import()，首次切换会有一次 ~10 KB 异步加载 ── 用户感知不到（< 50 ms）。

4字体回退机制

这是 i18n 章节里最容易翻车的设计点 ── mono 字体（SF Mono / JetBrains Mono / Cascadia Code）都不含 CJK 字符。处理不当会让中文 chrome 渲染成方框或回退到衬线字体（视觉不一致）。

4.2关键调整

03 § 6.1 字体栈已基本覆盖此场景（已含 PingFang SC / Microsoft YaHei UI 在 sans 栈末尾）。需要在 14 章新增 的事：

  • --font-mono 栈末尾追加 "PingFang SC", "Microsoft YaHei UI" ── CJK 字符在编辑器 / 树视图也能 fallback 渲染（不出现方框）
  • JSON 树视图 fs 微调：tree-view 当字符包含 CJK 时整行高度可能略升 ── 不调，让 line-height 1.7 自然吸收
  • 错误信息中包含 CJK：state bar fs 12.5 px + line-height 1.4 → CJK 字符勉强可读，不需要另开 fs；如视觉差再升 fs-sm（13）
  • placeholder 文案 i18n：所有 <input placeholder="..."> 必须用 t()，不能 hardcode

5.3初始化骨架（≤ 20 行）

// src/i18n/index.ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';

const NS = ['shell', 'panes', 'settings', 'history', 'errors', 'about', 'common'];

export async function initI18n(locale: 'en-US' | 'zh-CN') {
  const resources = Object.fromEntries(
    await Promise.all(NS.map(async (ns) => [
      ns, (await import(`./${locale}/${ns}.json`)).default,
    ]))
  );
  await i18n.use(initReactI18next).init({
    lng: locale, fallbackLng: 'en-US',
    resources: { [locale]: resources },
    interpolation: { escapeValue: false },  // React 已自动 escape
    ns: NS, defaultNS: 'common',
  });
}

5.4组件使用示例（≤ 15 行）

// src/shell/StatusBar.tsx ── 使用 useTranslation
import { useTranslation } from 'react-i18next';

export function StatusBar({ status, errorLoc }: StatusBarProps) {
  const { t } = useTranslation('shell');  // namespace = shell
  if (status === 'error' && errorLoc) {
    return <span>
      ● {t('statusBar.invalid')} · {t('statusBar.line')} {errorLoc.line},
        {t('statusBar.col')} {errorLoc.col}
    </span>;
  }
  return <span>● {t('statusBar.valid')}</span>;
}

8screen reader 关键流

三条核心交互必须通过 screen reader（VoiceOver）测试：

  1. 呼出浮窗 → 编辑器获焦：用户应听到"JSON editor, edit text" + tabBar 当前激活 Tab 名
  2. parse 错误：状态栏 aria-live="polite" → 自动朗读 "Invalid JSON, Line 3, Col 12"；详细 reason 由 inline lint tooltip 承载
  3. AI Fix 完成：DiffView Accept/Reject 按钮可 Tab；错误文本在 AI 面板内可读，未来 Toast 接入后再补 role="status"
