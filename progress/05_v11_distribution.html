二 · 5 个独立节点

3节点细节

3.1v11-N1 · homebrew tap（brew install jsonita）

项内容
目标版本v1.1（推荐先做 ── macOS 用户用 brew 最自然）
关键交付物新建 homebrew-jsonita tap 仓库；Casks/jsonita.rb 描述（url 指向 GitHub Releases dmg + sha256 + version）；CI release workflow 加一步自动 bump tap（用 actions/checkout + GitHub PAT 写 tap 仓库）
对接 spec12 § 9 分发渠道
用户安装命令brew tap jinhuang712/jsonita && brew install --cask jsonita
退出判据干净 macOS 机执行上述命令能装 + 启动
常见坑cask 仓库必须叫 homebrew-* 前缀（约定）；自动 bump 时 sha256 必须用已 staple 的 dmg；若用户名带大写，brew tap 名要全小写

3.2v11-N2 · npm 启动器（npx jsonita）

项内容
目标版本v1.2（次优先 ── Node 开发者群体常用）
关键交付物新 npm 包 jsonita（独立 repo 或 monorepo 子目录）；bin/jsonita.js 启动脚本：检测 OS → 下载对应 platform dmg/.exe → 运行；首次运行后落本地缓存避免重复下载
对接 spec12 § 9 分发渠道 v1.x 加 npm 启动器
用户启动命令npx jsonita 或 npm install -g jsonita && jsonita
退出判据干净环境 npx jsonita 能启动应用
关键决策npm 包仅是启动器（~5 KB），不把真正应用塞进 npm（违反 npm 大小约定 + 跨平台二进制混淆）
常见坑下载 dmg 后 macOS 仍需 staple 验证 ── 用 spctl --assess 提前确认；Windows 上要 spawn 而非 exec（避免阻塞 Node 主进程）

3.3v11-N3 · 自动更新（tauri-plugin-updater）

项内容
目标版本v1.1（与 N1 同期上 ── 这两个一起做能让 brew 装的用户也能收更新通知）
关键交付物接入 tauri-plugin-updater；生成 update signing key（不提交仓库，秘钥落本地 + GitHub Actions secrets）；CI release workflow 加 signature 生成 + latest.json 上传到 GitHub release artifact；应用启动时静默 check + 有新版时非阻塞 Toast 提示"有新版 X，点击重启更新"
对接 spec12 § 8 自动更新（v1.1+）
退出判据从 v1.0 升 v1.1（人造）能触发 Toast；点击重启后应用变 v1.1；签名验证通过
关键决策update key 与 codesign 证书分离（两个独立密钥；前者失泄不影响后者）；更新策略 = manual（用户点 Toast 才升，不偷偷升）；brew 装的用户 update 由 brew 管，应用层检测到是 brew 装的就跳过 in-app update（避免双源冲突）
常见坑signing key 一旦丢失所有旧版本用户的 updater 永久失效 ── 必须双备份（1Password + 离线 USB）；latest.json 的 URL 必须用 GitHub raw + tag 不变量，不要走 release asset（asset 改名会断）

3.4v11-N4 · Windows 完善（EV cert + winget）

项内容
目标版本v1.2 或 v1.3（受 EV 证书申请周期限制，可能比 N1 / N3 晚）
关键交付物EV code signing 证书（DigiCert / Sectigo）；signtool 签 .exe + .msi；提交 winget repo（microsoft/winget-pkgs）；Windows release CI workflow 加签名步
对接 spec12 § 6 Windows 签名（v1.1+）
退出判据Windows 11 上 winget install jinhuang712.Jsonita 能装；SmartScreen 不弹警告（EV 证书生效后立即降）
关键决策EV 证书必须用硬件 token（USB dongle）── 不能放 CI；签名走"本地 sign + 上传 artifact"（不在 CI 内做）；winget 提交需要 PR 到上游 repo，等 review
常见坑EV 证书申请要审 3-7 天；硬件 token 在 macOS 下不能用（开发机若是 macOS 要找 Windows 物理机 / VM）；winget 上游 review 周期可能 1-2 周

3.5v11-N5 · 日志导出 zip

项内容
目标版本v1.1（与 N1 / N3 同期 ── 实现成本低，对用户反馈链路价值高）
关键交付物Settings → About → "导出最近 7 日日志" 按钮；触发 IPC logs_export_zip；Rust 端 zip 含最近 7 个 daily log 文件 + metadata.json（app version / OS / 导出时间）；写到 ~/Downloads/jsonita-logs-YYYY-MM-DD.zip + Finder 弹文件位置
对接 spec15 § 10 用户视角 § 11 与其他章节对接 plan/01 F7
退出判据点击按钮 → 1-2 秒得到 zip；解压后 ≤ 7 个 daily 文件 + 1 个 metadata.json；日志内容仍受 RedactLayer 保护（无 API key / 无 JSON 内容）
关键决策导出前再次扫一遍 RedactLayer 黑名单（双保险）；不导出 SQLite db（个人历史不带出）；日志可能含路径名 ── 用户名做 ~ 替换后导出
常见坑zip 时 in-place 写可能与 tracing-appender 当前正在写的文件冲突 ── 复制到 temp 再 zip；> 5 MB 单文件 zip 时间会上去，给 progress UI

6已识别的实施风险

风险触发场景规避 / 应急
brew 自动 bump 把破坏版本推给所有 brew 用户release CI workflow 出问题 / 上 dmg 自身有 bugbrew bump 改成手动 PR（CI 出 PR，作者 review 后 merge）；首发问题版本立即出 patch + bump
updater signing key 丢失个人电脑硬盘损坏 / 误删双备份策略；首次生成立即备份到 1Password + 离线 USB；定期 verify 备份可用
EV cert 硬件 token 损坏USB token 物理故障 / 丢失EV 证书 CA 可补发但需 KYC 重做 ── 提前知道流程；备用方案：standard code signing 也能用（SmartScreen 警告一段时间会自动降）
winget 上游 review 卡住包名 / metadata 不规范提前看 winget-pkgs 已有 PR 学风格；review 卡住可在 Issue 区 ping maintainer
npm 包名 jsonita 已被占注册时发现已查重（CHANGELIST 0.1.0-plan 已记 "npm 无重名"）；若 v1.2 时被抢占，用 @jsonita/cli scoped
